Get started
Scan your own app in three commands
Free, offline until you point it at something, and nothing to sign up for. Works on Python 3.9 and later.
1
Install it
One dependency, no account, no API key. The attacks, the sample app and the benchmark are installed with it, so nothing else to download.
2
See what a scan looks like
Ten seconds against a deliberately vulnerable sample app: it scans, turns on defences one at a time and rescans, printing a grade each time.
3
Scan your own app
Sends the attacks to your endpoint and reports how many worked, with a 95% interval and the exact messages that got through. Add --canary with a test string from your system prompt to measure leaks, and --fail-over 0.05 to fail a build.
What it can and cannot see. A scan proves your app followed an instruction hidden in a user message, because the reply contains a random marker it was asked to join — an echo cannot do that. Attacks that arrive inside a retrieved document or a tool result are skipped, because only your app can feed those channels, and every report lists what it skipped. A clean result means these attacks did not work, not that the app is safe.

What it tests
Three apps, one attacker
The attacker controls some text each app reads. RAGProbe measures whether that text can take the app over — then whether a layered defence stops it.
Chat assistant
A support bot with a secret in its system prompt. Can a user talk it out, or hijack it?
RAG assistant
Answers from retrieved docs — one written by the attacker. Does the poison get retrieved, and obeyed?
Email agent
Reads and sends mail with tools. Can a planted email make it leak private data to an outsider?

Checkable, not guessed
Every runnable attack plants a secret canary, so success is scored by an oracle — no human judgement, no LLM-as-referee.
Tagged and split
Each item carries its OWASP risk, technique, language, source and licence, split into train / dev / test so detectors are reported only on held-out data.
Reproducible by design
Every run records a manifest — version, commit, model, seed, and a fingerprint of the exact attacks — and caches model replies, so a number repeats exactly.

Measured, not established
Both detectors caught less German than English
Two injection detectors on the labelled test split, split by language. Both caught roughly half as much German, and Meta’s Prompt Guard 2 almost none — but on 34 and 19 items neither gap is statistically significant.
Attacks caught (recall), by language
Higher is better · deepset/prompt-injections test split
Rule-based detectorMeta Prompt Guard 2
Prompt Guard 2 caught 24% of English attacks and 5% in German. Fisher’s exact test gives p = 0.13, so treat this as a reason to measure your own detector in your users’ languages, not as a proven gap.
Lab drill · simulated model
Against a model that obeys everything, the layered defence holds — and only there
A hardened prompt, data-marking, a detector, a tool policy and an output filter — stacked. Attack success falls from 92% to 0, with no legitimate requests wrongly blocked. On real models the same defence did not hold up: its one significant result lost significance once cut-off replies were excluded, and it did not repeat on a fresh set of attacks.
The victim here is a simulated model built to obey every instruction it can parse, so this measures the defences and the harness, not any real model. On real models the same defence clearly helped one of four — the honest version is in Real models above.

Attacks that don’t look like attacks
The numbers below come from a worst-case drill against a simulated victim, rebuilt on every push — including where the defences fall short.
Poisoned tools
The attacker's text hides in a tool description or a tool result and tells the agent to leak data. A rule about what a tool may do stops it however it arrives.
