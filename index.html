The regression gate

The same workflow as unit tests: write the expectation, record the baseline, fail the build on regression. Exit codes mean something: 0 passed, 1 a gate failed, 2 usage error.

  1. 1

    Write cases

    Describe a good answer in golden_set.yaml: expected chunks, keywords, refusals.

  2. 2

    ragprobe run

    Ingest the corpus, answer every case, score retrieval and answers, append the run to history.

  3. 3

    ragprobe baseline

    Promote the current behaviour to the regression contract and commit the file.

  4. 4

    ragprobe diff

    Re-run after every change. A regressed case fails CI with exit code 1.

ci - ragprobe diff
$ ragprobe run --html

Golden sets

A golden set is the regression contract in one YAML file. Every non-refusal case names the chunk ids that genuinely contain the answer; those drive precision@k, recall@k, hit rate and MRR. Chunk ids are heading anchors (doc#slug), so they survive re-chunking.

Cases can also require or forbid keywords, demand a refusal, and give a reference answer for the advisory judge.

cases:
  - id: pto-annual-allowance
    category: hr-policy
    question: How many days of paid time off do full-time employees get?
    expected_chunks: [employee_handbook#paid-time-off]
    required_keywords: ["20 days"]
    expected_answer: Full-time employees accrue 20 days of PTO per year.
  - id: remote-onsite-days
    category: hr-policy
    question: How many days per week are employees expected on site?
    expected_chunks: [employee_handbook#remote-work]
    forbidden_keywords: ["fully remote"]

Metrics

Six pieces, one package. Each writes to the same history.

Golden dataset

Questions with expected chunks, required and forbidden keywords and refusal rules, in one YAML file next to the code.

Retrieval metrics

precision@k, recall@k, hit rate and MRR, computed the strict way: precision divides by k and an undefined metric is null.

Answer evaluators

Keyword presence, forbidden terms, refusal in both directions, citation validity and an offline grounding check. The LLM judge is advisory.

Regression gate

ragprobe diff classifies every case as regressed, degraded, improved, flat, new or removed and exits 1 when the gate fails.

History & dashboard

Every run is appended to a history store. The dashboard plots trends, marks config changes and attributes failures to retrieval or generation.

Runs offline in CI

A deterministic stub provider means the same input gives the same output on any machine. No key, no network, no flaky baseline.

About RAGProbe

Prompt changes are code changes, but most RAG systems are tested by re-reading answers in a notebook, or by paying for an eval product that needs a key, a network and a budget. RAGProbe is the third option: a golden set and a diff that run offline, deterministically, and fail the build when a case gets worse.

Case study: a docs assistant over the Playwright guides

59 real Playwright guide pages (841 chunks), 62 questions written the way QA engineers ask them, four of them unanswerable. Same golden set through four configurations:

Configurationpass ratehit rate@3MRRout-of-scope refused
TF-IDF + stub, first run40.3%0.6030.5370 / 4
TF-IDF + stub, citation extractor fixed61.3%0.6030.5370 / 4
bge-small + stub59.7%0.7070.5920 / 4
bge-small + gemini-3.5-flash-lite48.4% → 53.2%0.7070.5924 / 4

Three findings. The first real run found a bug in the citation evaluator, not the pipeline (markdown links read as fabricated citations; 40.3% → 61.3% with retrieval untouched). A neural embedder improved every retrieval metric and did nothing for the pass rate, and the gate refused it: 8 cases regressed, 15 improved. A real model refused all four out-of-scope questions, exposed a second citation bug and a grounding heuristic calibrated on the wrong kind of answer (72.6% with it advisory), and left 17 failures the harness attributes as 13 retrieval, 4 generation.

Examples

Each example is a complete target. Copy the one closest to your stack next to your code and run ragprobe run --target <module>:<name>. None of these frameworks is a RAGProbe dependency.

  • langchain_target.py — LangChain retriever + chat model, wrapped as a class the harness calls per question.
  • llamaindex_target.py — A LlamaIndex query engine exposed as a single answer() function.
  • fastapi_service.py — Any service behind HTTP: uvicorn fastapi_service:app, then point --target at the URL.

Not deleted. Kept as documented failures. Two golden cases fail on the shipped configuration on purpose: they are real defects the harness found in its own pipeline, and a golden set that is green on day one is usually not asserting anything.

known_failure
Perfect retrieval, wrong answer

Every expected chunk came back at rank one; the answer still named the wrong plan tier. Attribution: generation.

known_failure
Sentence selection inside the right chunk

Retrieval found the chunk; the extractive answer picked the neighbouring sentence. The case stays so the fix can be measured.

Deleting a failing case does not help either: ragprobe diff counts it as removed and the gate fails.
